# 일공로그(10-Log) 출시 전 리팩토링 — 실행

아래 두 audit 리포트에 정리된 결과를 바탕으로, **P0 / P1 항목을 수정한다.**

- `docs/audit-web-2026-08.md` — 웹앱 + Supabase
- `docs/audit-mobile-2026-08.md` — 모바일 앱 + 웹/앱 경계

**시작 전에 두 리포트를 모두 읽는다.** 한쪽만 읽고 계획을 세우지 않는다. 두 리포트에 걸쳐 있는 항목(특히 WebView ↔ Native 메시지 계약, 웹/앱 중복 코드)은 **양쪽 레포를 함께 수정해야 하므로 반드시 한 묶음으로 처리한다.** 웹만 고치고 앱을 그대로 두면 메시지 계약이 깨진다.

리포트 중 하나에 접근할 수 없으면 즉시 알리고 진행 여부를 묻는다.

새 기능을 추가하는 작업이 아니다. **현재 기능을 그대로 유지하면서** 보안 취약점과 구조적 문제만 제거한다.

---

## ⛔ 절대 규칙

### 변경하지 않는 것

- 기존 기능 / 사용자 플로우 / UI / UX / 디자인
- Supabase 스키마, 기존 데이터 구조, API contract
- Push Notification 동작, WebView 동작, Navigation
- audit 리포트에 없는 코드

기능 변경이 불가피한 항목이 있다면 **먼저 이유와 영향 범위를 보고하고 승인을 받은 뒤** 진행한다.

### DB 변경 규칙

**Supabase MCP로 스키마·RLS·트리거·함수를 직접 apply 하지 않는다.** 프로덕션 DB에는 실제 사용자 데이터가 있다.

- 모든 DB 변경은 `supabase/migrations/YYYYMMDDHHMMSS_설명.sql` 파일 작성으로만 한다.
- `BEGIN` / `COMMIT` 트랜잭션 블록으로 감싸 부분 적용을 방지한다.
- 기존 정책을 교체할 때는 `drop policy if exists` 후 재생성하는 기존 마이그레이션 스타일을 따른다.
- 각 마이그레이션 파일 상단 주석에 **무엇을·왜 바꾸는지, 그리고 이 변경으로 기존 사용자의 정상적인 데이터 접근이 막히지 않는 이유**를 적는다.
- 적용은 사람이 검토 후 직접 수행한다. 적용했다고 가정하고 다음 작업을 진행하지 않는다.
- MCP 조회(읽기)는 현재 상태 확인 목적으로 자유롭게 사용한다.

### P0 처리 규칙

**P0 항목은 수정 계획을 먼저 제출하고 승인을 받은 뒤 손댄다.** 권한 정책 수정은 잘못되면 전체 사용자의 접근이 막힌다.

### 작업 브랜치

- **웹·모바일 두 레포 모두** `chore/pre-release-audit` 브랜치를 새로 만들어 작업한다. 배포 브랜치에서 직접 작업하지 않는다.
- 두 레포에 걸친 변경은 커밋 메시지에 같은 audit 항목 번호를 적어 짝을 이루게 한다.
- 커밋은 **항목 단위로 분리**한다. 하나의 커밋에 여러 audit 항목을 섞지 않는다. 되돌릴 수 있어야 한다.
- 커밋 메시지는 Conventional Commits 한국어. 본문에 대응하는 audit 항목 번호를 적는다.

```text
fix: journal_entries UPDATE 정책에 소유권 검증 추가

audit P0-02. WITH CHECK 절이 없어 user_id를 타인 것으로
변경할 수 있던 문제 수정.
```

## 우선순위 원칙

```text
보안 > 정확성 > 유지보수성 > 가독성 > 성능 > 코드량 감소
```

코드가 짧아지는 것보다 **이해하기 쉽고 안전한 구조**를 우선한다.

### 과도한 리팩토링 금지

- 최신 패턴으로 바꾸는 것 자체는 목표가 아니다.
- audit 리포트에 없는 코드는 건드리지 않는다. 작업 중 새 문제를 발견하면 수정하지 말고 별도로 보고만 한다.
- 파일 이동·이름 변경은 audit이 명시적으로 지적한 경우에만 한다.
- 새 라이브러리 추가는 최소화한다. 기존 dependency를 우선 활용하고, 추가가 꼭 필요하면 먼저 이유를 설명하고 승인을 받는다.

### 과도한 추상화 금지

코드가 비슷하다는 이유만으로 공통 컴포넌트나 추상화를 만들지 않는다. 아래를 모두 만족할 때만 공통화한다.

- 실제 역할이 동일한가?
- 동일한 책임을 가지는가?
- 앞으로 함께 변경될 가능성이 높은가?
- 공통화 후 props와 의존성이 지나치게 복잡해지지 않는가?

공통화가 오히려 복잡해진다면 분리된 상태를 유지하고, 그 판단 근거를 최종 보고에 남긴다.

## 작업 순서

### Phase 1 — 계획 수립 (코드 수정 전, 승인 필요)

두 audit 리포트를 읽고 이번에 처리할 항목을 선정해 계획을 제출한다. 각 항목마다:

- audit 항목 번호와 제목 (출처 리포트가 web인지 mobile인지 표시)
- 현재 문제
- 수정 방법 (구체적으로)
- 변경할 파일 목록
- 영향 범위 — 이 변경으로 동작이 달라질 수 있는 기능
- 예상 위험 및 롤백 방법
- 검증 방법

**P0 → P1 순으로 정렬한다.** 처리하지 않고 남길 항목이 있다면 그 이유도 함께 적는다.

계획 제출 후 **승인을 기다린다.** 승인 없이 Phase 2로 넘어가지 않는다.

### Phase 2 — 수정 실행

승인된 계획대로만 수정한다. 항목 하나를 끝낼 때마다:

1. 변경 내용을 요약해 보고
2. `npx tsc --noEmit` 실행
3. 커밋

계획에 없던 수정이 필요해지면 **멈추고 물어본다.**

### Phase 3 — 보안 재검증

수정이 끝나면 audit에서 P0/P1로 분류됐던 보안 항목을 다시 확인한다.

- RLS 정책 (새 마이그레이션 파일 기준으로 시뮬레이션)
- 인증 / 인가 / IDOR
- Secret, API key 노출
- WebView 설정, Native bridge 메시지 검증
- 입력 검증, 민감 데이터 노출

**특히 정책 변경이 기존 사용자의 정상적인 데이터 접근을 막지 않는지 확인한다.** 각 테이블에 대해 "본인 데이터는 여전히 CRUD 가능한가"를 정책 조건식 수준에서 검토한다.

### Phase 4 — 검증

**에이전트가 직접 실행할 것** (실제 명령 출력을 보고에 포함):

- `npx tsc --noEmit`
- `npm run lint`
- `npm run build`
- 모바일 레포도 동일하게 타입 체크 / 린트

**에이전트가 실행할 수 없는 것** — 체크리스트로만 출력하고, 확인했다고 쓰지 않는다:

- 실기기/시뮬레이터 WebView 동작
- Google OAuth 로그인 및 세션 주입
- 푸시 알림 수신 및 권한 플로우
- 실제 계정 2개로 데이터 격리 테스트
- 마이그레이션 적용 후 기존 사용자 CRUD 동작
- 주요 화면(캘린더 / 통계 / 회고 / 더보기) 수동 확인

실행하지 않은 검증을 통과했다고 기록하지 않는다.

## 최종 보고

**발견·수정 사항이 있는 항목만 작성한다.** 빈 섹션을 억지로 채우지 않는다.

### 1. 요약

- 처리한 항목 수 (P0 / P1 / 기타)
- 처리하지 않고 남긴 항목과 그 이유
- **출시 가능 여부 판단**과 남은 리스크

### 2. 보안 수정

심각도별로. 각 항목마다 `문제 → 위험 → 수정 내용 → 검증 방법`.

### 3. 코드 변경

Frontend / App / Backend로 나눠 무엇을 왜 바꿨는지.

### 4. 중복 처리

- **제거**: 실제로 삭제한 중복 코드
- **공통화**: 하나로 합친 코드
- **유지**: 중복처럼 보이지만 플랫폼·책임 차이로 유지한 코드 **+ 유지 이유**

### 5. DB 마이그레이션

작성한 마이그레이션 파일 목록과 각각의 목적. **아직 적용되지 않았음을 명시한다.**

### 6. Production Readiness

아래 항목을 `PASS / WARNING / FAIL / 미검증`으로 표시한다. 실제로 확인하지 않은 항목은 반드시 **미검증**으로 표시한다.

Security · Authentication · Authorization · RLS · API · Frontend · App · WebView · Push Notification · Database · TypeScript · ESLint · Build · Environment · Dependency

### 7. 변경 파일 목록

각 파일마다 무엇을 바꿨는지 한 줄 설명.

### 8. 사람이 해야 할 남은 작업

마이그레이션 적용, 키 교체, 수동 테스트 등 순서대로.
